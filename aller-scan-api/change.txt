Known mismatch: assumed products API contract vs actual implementation
========================================================================

tests/test_api/test_products.py has a section (top, "assumed contract")
that encodes an aspirational API spec for the products endpoints. The
routes as actually implemented (app/routes/products.py) differ from it.
This is documented in tests/README.md as a deliberate, not-yet-resolved
design gap - left as-is per project decision on 2026-09-05.

Mismatches (7 failing tests):

1. POST /api/v1/products/ has no auth requirement.
   - Assumed: requires auth, 401 if missing.
   - Actual: anyone can create a product, no auth dependency on the route.

2. Duplicate barcode on create returns 400, not 409.
   - Assumed: 409 Conflict.
   - Actual: raises HTTPException(400, "Product already exist") before
     the insert is even attempted (the 409 DuplicateKeyError branch in
     the same handler is dead code - the 400 check always fires first).

3. Single-product lookup path differs.
   - Assumed: GET /api/v1/products/{barcode}
   - Actual: GET /api/v1/products/get_by_barcode/{product_barcode}
     (there's also GET /api/v1/products/get_by_id/{product_id} for UUID
     lookups, not covered by the assumed contract at all).

4. List/search endpoint differs in method, path, and params.
   - Assumed: GET /api/v1/products/ with query params q (name substring),
     limit, skip.
   - Actual: POST /api/v1/products/list_of_products with a JSON body
     (ProductFilter: brand, product_name, allergens) plus limit/offset
     query params. No GET /api/v1/products/ route exists at all (hits
     405, since GET /api/v1/products/{something} conflicts with the
     get_by_barcode-style routes).

GET /api/v1/products/brands (the actual, already-implemented endpoint)
is unaffected by any of the above - it was a separate bug (Beanie
FindMany has no .distinct(); fixed by using
Product.get_pymongo_collection().distinct("brand")).

Resolution options considered (not applied):
- Implement the assumed contract (add auth, add /products/{barcode} and
  GET /products/ list+search, change duplicate response to 409).
- Rewrite the assumed-contract tests to match the actual routes.

Neither was applied; this file just records the gap for whoever picks
it up next.


z-dev branch: allergen cross-check wiring (2026-09-06)
========================================================

Backend (aller-scan-api):

1. Wired the allergen check into the product-scan flow.
   - POST /user-properties/scan-history used to trust client-supplied
     `status` and `detected_allergens` verbatim (ScanHistoryCreate).
   - Now the route looks up/creates a cached AllergenProfile for the
     scanned barcode from the product's `allergens` field, cross-checks
     it against the scanning user's AllergyPreference, and computes
     `status` (safe/dangerous) and `detected_allergens` itself.
     `status`/`detected_allergens` were removed from ScanHistoryCreate -
     they're server-computed now, not client input.
   - Extracted `get_or_create_profile()` and `matched_user_allergens()`
     into app/services/allergen_detection.py so /allergens/check and the
     scan-history route share one implementation instead of duplicating
     the cache-lookup + cross-check logic.

2. Swapped the allergen reference table (app/data/allergen_reference.json)
   from a hand-picked ~9-category list to the EU's 14 regulated allergens
   (Regulation (EU) No 1169/2011, Annex II): cereals containing gluten,
   crustaceans, eggs, fish, peanuts, soybeans, milk, tree nuts, celery,
   mustard, sesame, sulphur dioxide/sulphites, lupin, molluscs. Category
   keys and display names changed (e.g. wheat_gluten -> gluten_cereals,
   "Milk / dairy" -> "Milk", tree_nut -> tree_nuts, soy -> soybeans;
   shellfish split into crustaceans + molluscs). Tests asserting the old
   keys/display names were updated to match.
   - Still no citation/source pinned in the data file itself, and it's
     still a hand-typed synonym list, not derived from an ingredient
     ontology - matching is still naive substring containment (see the
     `ponytail:` comment in allergen_detection.py). Swapping the *list*
     of categories doesn't fix the *matching* method.

Frontend (aller-scan):

3. Removed the redundant client-side allergen comparison in the scan
   flow. aller-scan/src/api/scans.ts used to fetch the user's allergies
   and run its own naive exact-match comparison (api/alerts.ts), then
   send the computed status/detected_allergens to the backend - which,
   after (1), ignores those fields and computes them itself. Deleted
   alerts.ts and stopped sending status/detected_allergens from
   scanProduct(); Alert.tsx already reads status/detected_allergens from
   the scan-history response, so no UI change was needed.

Not done / still open:
- No real barcode decoding - BarcodeScanner.tsx shows camera video and
  takes typed/manual entry, it doesn't decode a barcode from the image.
- No ingredient-list parsing - detection still runs against the flat
  `Product.allergens` list (populated manually or from Open Food Facts'
  `allergens_tags`), not a full ingredients string.
- The products API contract gap above (mismatches 1-4) is unrelated and
  still unresolved.
